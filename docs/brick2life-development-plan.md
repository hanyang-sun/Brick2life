# Brick2Life 开发安排

更新：2026-10-20。用户确认 Brick2Life 为唯一活动主线。旧系统归档到 Assets 外，以下安排替代 2026-10-15 的旧模块复用计划；原计划保存在历史归档中。

## 当前范围

10×10、单层、等大积木、固定透视实验相机，按需采集。当前具备仿真编辑、相机/光照参数、配对 PNG/JSON、独立核心和确认会话。视觉识别、反馈绘制和投影联调仍待完成。

第一轮反馈限定暴露底板。积木顶面与底板处于不同高度，B 的格位定位必须处理透视高度偏移，C 的底板映射通过独立测试点验收。多层、连续识别、隐藏层推断与真实设备后续分别设计。

## 模块与责任

| 负责人 | 主文件范围 | 接口交付 |
| --- | --- | --- |
| A | Core/Contracts、Simulation、Editor、默认布局检查 | 维护棋盘定义和仿真；通过 CaptureFrame 提供 RGB 与独立评价 GT；维护公共合同兼容性 |
| B | 后续 Vision、Core 的差异逻辑、识别回放检查 | RGB/公开标定到 FrameObservation；固定格位、可配置颜色、未知和拒绝；不读取 GT 或编辑动作 |
| C | 后续 Projection、Application 中的应用规则、平面反馈场景 | 确认快照/差异到反馈；公开底板到输出的标定，测量中心和边缘误差 |
| 集成负责人（建议 A） | Application/BoardSyncSession、组合入口及联合验收 | 请求关联、确认/拒绝、旧帧和标定失效、投影清空与恢复；共用场景和构建设置统一修改 |

Core、Application 无 Unity 引用。公共合同放在 Core/Contracts，不单独建立 Contracts 程序集。Vision/Projection 随具体代码落地，再建立所需程序集。后续算法迁入经过源码和授权审查，不依赖整套旧 BrickDefense。

## 下一批交付

1. B 先用固定采集样本输出公共 FrameObservation，校验棋盘边缘与中心的格位，不以相对最左/最上积木作为原点。
2. C 用明确标记的人工快照独立验证平面内容与输出映射，暂不作为识别闭环证据。
3. 组合入口把采集图像和公开标定交给 B，通过 BoardSyncSession 确认，再把快照和差异交给 C。采集/识别异常调用 Fail，取消调用 Cancel。
4. 接入反馈时统一执行清空反馈、等待稳定、采集、分析、确认、恢复显示；异常和取消也恢复上次有效反馈。
5. 以少量固定布局/操作回放验收，再增加光照、遮挡和反馈干扰种类。大规模数据集方案仍处于撤回状态。

## 验收

- 相同布局重复采集不增加确认状态版本；移动边缘积木不使其他积木整体漂移。
- 初次确认明确建立基线。之后增删、改色与格位移动产生对应差异；同色身份不明确时保留歧义，不伪造实例移动。
- 未知占用/颜色、错误帧、标定失效和失败均保留上次确认状态，可重试。
- 真实布局被可靠识别但应用无路时，确认布局并由应用提示问题。
- 第一阶段如采用塔防，战斗使用开局确认快照；局中改图另行设计。
- 独立记录图像、标定、预测、确认版本、差异、阶段耗时和反馈误差。GT 只供评价。
- 中心和边缘测试点独立于拟合点；仿真误差与真实设备实测分别报告，不将独立显示窗口作为实体投影对齐通过。

实际目录、确认接口与当前验证结果以 [架构说明](architecture.md) 为准。
