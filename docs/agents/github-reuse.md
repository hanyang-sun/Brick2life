# GitHub 检索与有限借鉴

本规则适用于新功能、现有功能扩展和功能重写。以同类项目的已有实现为开发起点，按本项目需求选择性整合和适配。

## 编码前的步骤

1. 从当前用户任务、`README.md`、`docs/architecture.md` 和 `docs/brick2life-development-plan.md` 明确范围与验收条件；旧规格位于 `Archive/BrickDefense/docs/`，仅在明确迁入旧算法时查阅。
2. 在 GitHub 检索相同或相近功能的项目；可使用 GitHub 搜索或限定 `github.com` 的网络搜索。记录检索日期、关键词和真实仓库链接。
3. 阅读候选项目的 README、相关源文件及许可证。比较功能匹配程度、Unity/C# 兼容性、Android 离线运行能力、依赖成本和维护情况。候选充足时比较至少两个；候选较少时如实记录结果。
4. 汇总各候选中可采用的部分，明确选择哪些机制、组件或代码，以及如何适配本项目接口。把结论写入 `docs/research/<feature-slug>-github.md`。

只有记录包含已检索的范围、实际阅读的实现、候选比较、授权情况和具体借鉴方案，才完成编码前检索。仅列仓库名称或阅读搜索摘要不足以完成这一步。

## 有限借鉴的方式

- 按功能需要选择少量组件或实现，优先采用兼容的现成组件，或对已有实现做局部适配。
- 本项目的需求、数据接口和验收条件决定最终行为；记录参考实现与需求的差异，并编写必要的衔接代码。
- 直接复制、改写或引入外部代码前确认其授权条件；未确认授权时只作思路参考。
- 保留采用代码的版权与许可证声明，在 `THIRD_PARTY_NOTICES.md` 中记录来源、版本或提交、采用范围及修改内容。该文件在实际采用外部代码时创建。
- 若没有找到合适项目，记录检索范围与不适用原因，继续寻找相关算法或组件的实现依据。无法完成检索或缺少可用依据时报告该功能的阻塞原因，先推进不依赖它的工作。
- 实现完成后，按本项目验收条件验证行为，并说明借鉴了什么、做了哪些适配。

## 检索记录的最少内容

- 功能范围、验收条件、检索日期和关键词。
- 候选比较表：仓库链接、读过的相关文件或提交、许可证、匹配点、差异、采用或放弃原因。
- 整合方案：采用的机制或代码、引入方式、接口适配和验证方法。

区分思路参考、代码改编和直接依赖；记录与最终实际采用的方式保持一致。
