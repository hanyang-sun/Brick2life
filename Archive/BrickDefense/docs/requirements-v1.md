# 实体积木塔防项目：首版需求与接口规范

当前照片入口以 [v1.2 无格纸规范](requirements-plain-only-v1.2.md) 为准；本文的格纸定位要求作为历史版本保留。

**版本：v1.0｜日期：2026-10-07｜状态：首版功能与接口终稿。**

本文固定首版的产品范围、规则、模块接口和验收方法。积木尚未到货，因此实际颜色、毫米尺寸、视觉阈值、手机性能上限和战斗平衡数值列在第 9 节作为**实测配置项**；它们没有被虚构为已知结果。开发与验收使用同一份配置记录。后续改变本文的功能规则须更新版本，不把实测配置的填写误当成功能变更。

依据：项目书《基于实体积木三维重建的虚实融合塔防关卡生成系统(1).txt》、项目讨论及第一张彩色小立方体参考图。首版采用项目书基础要求的**实体规则网格摆放**；过去讨论过的实体自由摆放方案不再适用。

## 1. 目标与范围

玩家在实体方格底纸上搭建单层彩色立方体布局，用 Android 手机离线俯拍；系统恢复每块积木的实体格位和颜色，生成固定大小的 Unity 三维塔防关卡。玩家核对地图、点选敌人出生点、设置波次参数并主动开始游戏。一局开始前或结束后可重新摆放、重新扫描并生成新关卡。

首版只处理第一张参考图所示的**同尺寸普通立方体积木**、一张俯拍 RGB 照片和单层摆放。三维关卡使用已知立方体尺寸与恢复的平面格位搭建；首版不声称从单张俯拍图独立恢复堆叠高度或不可见表面。手机在断网状态下必须完成拍照、识别、关卡生成和游玩；电脑只用于开发与测试。

首版不包含：第二张参考图中的长条或竖立构件、堆叠与遮挡恢复、多视角融合、对局中实时重扫或局部更新、摄像头实景上的实时 AR 叠加、iOS、升级系统、玩家逐格手动修图，以及多种颜色共同代表同一种角色。这些均属于后续版本。

## 2. 实体摆放与拍摄规范

| 项目 | 首版规则 |
| --- | --- |
| 格纸 | 可打印的 **10×10 正方形格纸**；每个可用格的边长等于到货后测得的积木边长。格纸另有不放积木的外侧定位边，四角可识别，并在外侧放置非对称方向标记以指定左上角。具体图案属于制作细节。 |
| 摆放 | 一格最多放一块积木；积木单层放在格内，顶面边缘与格线平行。可跳过任意数量的**完整格位**形成空位；不允许积木跨格、叠放或遮住外侧定位标记。同色相邻、紧贴的积木仍须按格位分别识别。 |
| 取景 | 手机竖直向下拍一张照片；屏幕显示正方形扫码式取景框。整张格纸、四角、方向标记和全部积木均须完整入框，并留少量画面余量。拍摄尺度、斜拍、模糊和摆放偏差的数值容差通过实拍校准。 |
| 超界或不确定 | 格纸定位失败、定位区域被裁切、某格空/占状态或颜色无法可靠判定、积木跨格时，扫描被拒绝并给出原因。已可靠识别但未映射到游戏角色的颜色由关卡校验拒绝。玩家调整后重拍。完全位于画面外的物体无法由图像检测，拍摄引导需提醒玩家把全纸入框。 |
| 重扫 | 开局前和一局结束后允许全量重扫；对局中不更新地图。同一格纸上的同一摆法应恢复相同实体行列，实际重复性由实拍验证。 |

### 2.1 两套网格

- **实体格网：**列 `c`、行 `r` 均取整数 `0…9`。格纸方向标记指定左上角 `(0,0)`；列向右、行向下。每块积木对应一个实体格位。
- **游戏寻路网格：**`x`、`y` 均取整数 `0…19`，方向与格纸一致。实体格 `(c,r)` 固定映射到 `(2c,2r)`、`(2c+1,2r)`、`(2c,2r+1)`、`(2c+1,2r+1)` 四个游戏格。一个积木因此占四个寻路格，但在三维场景中仍只生成**一个**对象。
- **图像与游戏位置：**保留照片中的测量位置供诊断和实验；Unity 对象摆放在恢复的实体格规范中心。不能把屏幕取景框左上角误当作桌面格纸原点，不能按最外侧积木临时重设边界。

## 3. 扫描到游玩的流程

1. 玩家把积木摆在格纸上，在手机取景框内拍照。采集模块统一图像方向。
2. 视觉模块先定位格纸四角与方向标记，建立 10×10 格网；再逐格判断空/占并识别颜色。占格各生成一个独立积木记录。同色相邻不能被合并为一块。
3. 扫描失败时显示位置与原因，仅允许调整摆放或重拍。扫描成功时显示 10×10 数字地图、每块的颜色及固定角色和数量；玩家确认正确，发现错误则重拍。首版无逐格手动修改。
4. 系统把实体格确定性映射为 20×20 游戏格。玩家在空白游戏格点选**一个**出生点，边缘或内部均可。系统校验占用和到至少一块核心的路径，并预览路线；无效时让玩家重选出生点或调整实体布局重拍。
5. 玩家在开局前填写波次参数；校验成功后进入独立的 Unity 三维关卡。包括第一波在内，每波均由玩家点击开始。对局中地图不变。
6. 一局结束后，玩家可改变实体布局并重新扫描，生成另一局新关卡。

## 4. 颜色、关卡与战斗规则

### 4.1 颜色与角色

首版只使用三种游戏角色：**核心、墙、防御塔**。每种角色对应一种固定实体颜色，玩家不在每局扫描后重新指定。实际三种颜色标识须在积木到货后填入 `LevelRules.colorRoleMap`；积木识别模块只报告物理 `colorId`，不把某个颜色硬编码为游戏角色。首版若扫描到未映射颜色，提示“不支持的积木颜色”并拒绝生成关卡；这是一条接口默认规则，不扩展出第四类角色。空实体格对应可走区域。

关卡至少有一块核心，可有多块且可分散摆放；所有核心共用**一条生命值**。墙和塔占用的四个游戏格均不可通行；核心占用的格是敌人可进入的目标格。首版不要求每一关必须有墙或塔；只有核心但无塔的关卡可以开始并可能失败。

### 4.2 寻路与出生点

敌人从玩家选的一个空游戏格出生。A* 仅允许上下左右四方向，每走一格代价相同，不允许对角线或穿过墙、塔。目标是**最短可达**的一块核心，进入其任意一个游戏格即视为抵达；多块核心中至少一块可达即可。若没有核心、出生点被占用或没有可达核心，不允许开局。多个核心等距时采用固定的行列顺序选目标，具体等长路线可由实现稳定决定。

### 4.3 塔、怪物与胜负

- 一块塔积木生成一座塔；塔自动攻击射程内距离最近的存活敌人。首版墙只阻挡移动，不做塔攻击的遮挡判定。射程以游戏格为单位，数值在试玩配置中确定；所有塔使用同一套基础伤害、射程与攻击间隔。
- 怪物按 A* 路线以玩家设定的速度移动。塔攻击使怪物生命值降到 0 或以下时怪物死亡并离场；怪物抵达任意核心后离场，给共享核心生命造成玩家设定的伤害。
- 共享核心生命降到 0 或以下时立即失败。当前波的怪物全部生成且场上已无存活怪物后，才允许玩家点击开始下一波。最后一波满足该条件且核心生命仍大于 0 时获胜。

### 4.4 波次输入

玩家开局前设置同一份 `WavePlan`，所有波次的每波怪物数量与怪物属性相同：

| 字段 | 含义 | 输入约定 |
| --- | --- | --- |
| `waveCount` | 波数 | 正整数 |
| `enemiesPerWave` | 每波怪物数 | 正整数；总出怪数为两字段乘积 |
| `enemyHealth` | 每只怪物生命值 | 正整数 |
| `enemySpeed` | 移动速度 | 有限正数，可带小数，单位为游戏格/秒 |
| `coreDamage` | 抵达核心造成的伤害 | 正整数，与核心生命同一数值尺度 |
| `spawnInterval` | 同一波相邻两只怪物生成的间隔 | 有限正数，可带小数，单位为秒 |

空值、0、负数、非数字或超过已配置设备上限的值不能开局，界面指出错误字段。第一波开始后本局 `WavePlan` 锁定。具体输入上限与默认数值在 Android 真机测试后写入版本配置；不能因尚未实测就允许无限制出怪。塔基础参数与共享核心初始生命在 `CombatConfig` 中配置，玩家首版不直接修改；升级系统后续再加入。

## 5. 模块与数据接口

接口描述调用者必须知道的字段、约束和失败结果，不规定 C# 类名或识别算法内部实现。模块顺序为：

`采集 CaptureSet → 格纸定位与逐格识别 ScanResult → 游戏格映射 GridResult → 关卡校验 LevelResult → 游戏运行 GameState`。

| 数据 | 最少字段 | 关键约束 |
| --- | --- | --- |
| `CaptureSet` | `scanId`、`frames[]`、`primaryFrameId` | 首版恰好一张俯拍照片；数组结构保留以后增加其他视角的可能。 |
| `ImageFrame` | `frameId`、RGB 图像、宽高、方向、取景框像素区域、拍摄时间 | 采集模块把方向归一；原图不被后续识别结果改写。 |
| `BoardObservation` | 按方向标记排序的四角、方向、格纸到图像的变换、可信状态 | 格纸不完整或方向无法确定时不能宣称定位成功；图像与格纸坐标保持可追溯。 |
| `PhysicalCellObservation` | `c`、`r`、`state`、`confidence`、`brickId?` | `state` 为 `empty/occupied/uncertain`；成功扫描恰好给出 100 格，每个占格指向一块积木。 |
| `BrickObservation` | `brickId`、`c`、`r`、`colorId`、`confidence`、`evidence[]` | `brickId` 在一次扫描内唯一；同色相邻格有不同编号；证据关联照片编号、图像中心与可见区域。首版不伪造从图像恢复的堆叠高度。 |
| `ScanResult` | `scanId`、`status`、`board?`、`physicalCells[]`、`bricks[]`、`issues[]` | 只有格纸定位可靠、100 格空/占确定且所有积木颜色明确时 `status=success`；否则 `rejected`，可保留部分证据用于提示和实验。 |
| `GridResult` | `sourceScanId`、`status`、`placements[]`、`navCells[400]`、`issues[]` | 只接受成功扫描；每个实体格映射四个游戏格；一个占格只有一个来源 `brickId`，同一块积木只有一个三维对象。 |
| `LevelRules` | `colorRoleMap`、移动与核心规则、塔攻击规则 | 首版三种颜色与三种角色固定一一对应；未分配颜色导致关卡拒绝，不在识别模块硬编码角色。 |
| `SpawnSelection` | `x`、`y` | 一个 `0…19` 的游戏格坐标；必须为空且到至少一个核心可达。 |
| `LevelResult` | `status`、`entities[]`、`cells[400]`、`spawn`、`coreBrickIds[]`、`targetCoreBrickId?`、`route[]`、`issues[]` | 只有 `success` 可进入游戏；`entities[]` 每块积木一项，`route[]` 是四方向最短路线；多个核心只对应一条共享生命值。 |
| `WavePlan` | 第 4.4 节六项字段 | 属于本局游戏配置，不属于扫描结果；首波开始后不可修改。 |
| `CombatConfig` | `initialCoreHealth`、`towerDamage`、`towerRange`、`towerAttackInterval` | 本版所有核心共享前一字段，所有塔共用后三字段；具体数值待试玩。 |
| `RuntimeLimits` | 玩家输入各字段上限、最大总出怪数 | Android 真机测试后写入版本配置；输入超限时返回字段级错误。 |
| `GameState` | 阶段、共享核心生命、当前波、已出怪数、场上敌人 | 阶段至少区分待首波、出怪中、清场中、待下一波、胜利、失败；游戏状态不回写照片或扫描证据。 |
| `Issue` | 稳定错误代码、受影响对象/格位、用户可读提示 | 模块调用者根据错误代码处理，不解析中文提示。 |

建议至少区分以下错误类别：拍摄失败、格纸缺失或裁切、方向不明、图像质量不足、积木跨格、格位状态不确定、颜色不确定或未映射、缺少核心、出生点被占用、无可达路线、波次输入无效。具体代码命名由实现统一，拒绝原因应能用于统计，不把自动识别失败当作成功样本。

## 7. 验收方法

### 7.1 功能验收

1. Android 断网时能从拍照完成识别、预览、出生点选择、波次设置、三维塔防游玩和胜负结算。
2. 第 6 节示例的实体格、游戏占格、对象数量与寻路结果符合预期；同色相邻的两个占格仍产生两个 `brickId`。
3. 格纸被裁切、方向不明、颜色或格位无法判定时，显示具体原因并拒绝进入游戏；不能以错误合并结果宣称扫描成功。
4. 至少演示一次有效关卡、一次无路关卡被拒绝、一次重新摆放后重扫生成新关卡；验证多核心共血、玩家手动开始每波和胜负条件。

### 7.2 实物与性能评价

到货后建立人工标注样本，至少覆盖普通布局、空格较多、同色两块并排、三块成排、2×2 紧贴、不同光照、轻微斜拍、多核心、道路封闭和重扫。逐次保存原图、人工真实格位与颜色、自动结果、拒绝原因和耗时。至少报告：

- **积木识别正确率：**逐块统计颜色及位置均正确的比例，另报漏检、误检和拒绝扫描比例。
- **实体格位恢复正确率：**按真实 `(c,r)` 与恢复结果逐块比较；这对应项目书的网格位置恢复指标。
- **同色紧贴整例正确率：**同色贴合样本中，块数、每块格位和颜色全部正确的案例比例；仅提示重拍不算识别正确。
- **游戏格占用正确率：**按固定 2×2 映射与人工真值比较 400 个格的状态。
- **有效关卡生成率与无效关卡拒绝率：**有效布局中正确生成可玩地图的比例，及无效布局中正确拒绝的比例。
- **处理时间：**分别测量拍照完成至识别预览、确认地图至进入三维关卡的时间，并记录测试设备。

样本量、数值通过门槛和性能上限必须在真实积木与 Android 真机试验后写入验收记录；本文不填未经实测的百分比或毫秒数。

## 8. 首版之后的扩展

保留 `CaptureSet.frames[]` 与 `BrickObservation.evidence[]`，便于以后加入其他视角照片；是否进一步支持堆叠、遮挡和高度恢复需另立需求。多色共用角色、塔升级、对局中连续扫描、局部地图更新、实时 AR 和第二类积木均需独立设计，不改变首版已确认的离线单次扫描流程。
