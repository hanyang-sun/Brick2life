# Brick2Life 开发方案与仓库过渡

状态：规划与分支准备；以下 Brick2Life 功能尚未实现。更新日期：2026-10-15。

## 目标和第一阶段边界

仓库继续沿 `main` 开发，BrickDefenseMVP 作为历史原型保留。Brick2Life 的主线是：虚拟积木布局 → 顶部相机识别实体布局 → 检测已确认布局的变化 → 更新塔防路线、射程和游戏状态 → 将反馈投回实体桌面。依据是工作区 `Doc/06方向调整/桌面投影实体积木塔防_方向调整草案_2026-10-14.md`；该文件仍是草案，设备型号、尺寸和预算未定。

第一阶段限定单层、等大积木，沿用 10×10 实体格和核心、墙、塔三类玩法角色。用户手离开后主动触发一次采集；必要时采集前暂时清空投影，识别确认后恢复显示。首次验收的操作是移动一块墙、触发更新、得到新路线并将路线准确显示在桌面上。战斗使用开始时确认的布局快照；对局中实时改图不在第一阶段。

在没有实际投影设备时，可以用独立显示窗口验证平面输出及坐标映射，但这不构成桌面投影对齐验收。投影仪、相机与底板固定后，必须用实体测试点测量桌面中心和边缘的误差。

## 首阶段验收

1. 虚拟编辑与实体识别生成相同坐标系的棋盘快照；颜色本身不固定等于游戏角色。
2. 固定相机下，相同布局重复采集不报告变化；移动一块墙只产生相应的格位变化，不因相对原点变化而使其他积木整体漂移。同色积木无法唯一匹配时标记歧义，不伪造身份。
3. 遮挡、模糊、标定失效或识别拒绝时，上一份已确认布局和游戏地图保持不变，记录失败原因并允许重采集或人工校对。
4. 确认新布局后，现有寻路重新计算，桌面平面输出显示新路线和射程；无法通行时显示明确问题。游戏开始后保持布局快照锁定。
5. 保存采集图、标定版本、前后快照、变化事件及采集/分析/确认/显示时刻；实体投影验收记录中心与边缘测试点的物理误差和失败恢复过程。数值门槛由设备预试验后确定，不用模拟显示代替实测。
